# Canonical feature inventory

Contract 1.0; source of truth: src/contracts.py, FEATURE_NAMES. All features use events strictly before the cutoff. Order below is serialization/API order.

| # | Name | Definition |
|---|---|---|
| 1 | recency_days | Whole days since latest positive invoice |
| 2 | frequency | Distinct positive invoices |
| 3 | monetary_total | Sum of positive line totals, GBP |
| 4 | monetary_mean | Mean positive invoice value, GBP |
| 5 | monetary_std | Sample standard deviation of invoice values; one invoice → 0 |
| 6 | days_since_first_purchase | Whole days since first positive invoice |
| 7 | avg_days_between_orders | Mean whole-day invoice gap; one invoice → tenure |
| 8 | std_days_between_orders | Sample gap deviation; fewer than two gaps → 0 |
| 9 | is_one_time_buyer | Exactly one positive invoice → 1 |
| 10 | avg_basket_size | Mean number of transaction lines per positive invoice, not units |
| 11 | avg_basket_value | Mean invoice value; currently redundant with monetary_mean |
| 12 | max_basket_value | Maximum invoice value, GBP |
| 13 | avg_unique_items_per_basket | Mean distinct StockCodes per invoice |
| 14 | single_item_basket_ratio | Fraction of invoices with exactly one line |
| 15 | top_category_share | Largest spend share by first description token |
| 16 | n_unique_categories | Distinct first-token proxy categories |
| 17 | category_entropy | Base-2 Shannon entropy of category spend shares |
| 18 | has_ever_cancelled | Any C-prefixed historical invoice → 1 |
| 19 | cancellation_rate | Cancelled invoices / all distinct historical event invoices |
| 20 | return_rate | Absolute negative units / all absolute event units |
| 21 | weekend_purchase_ratio | Positive invoices on Saturday/Sunday / positive invoices |
| 22 | morning_purchase_ratio | Positive invoices before noon / positive invoices |
| 23 | country_code | Majority country; map fitted at earliest training cutoff; unseen → −1 |
| 24 | is_domestic | Majority country is United Kingdom → 1, not Québec |
| 25 | n_countries | Distinct countries in positive purchase history |

Fixed outlier caps precede these calculations. Ratios are bounded 0–1, binary flags are 0/1, unknown country alone may be −1. Structural defaults above are explicit. Remaining missing numeric values are left for a median imputer fitted only on the estimator's training rows.

The API requires all 25 finite numbers and rejects missing/extra keys, strings, booleans, infinities, NaNs and invalid ranges. The saved historical feature store supports the demo; it is not a live feature-computation service. Category taxonomy and ordinal-country encoding require further study.

## Data-minimisation audit

The brief (section 3.7) asks of every feature: is it necessary? `python -m src.minimisation` answers with a drop-column test on development data only:

- **Refit without the feature.** The selected pipeline is refit without one feature, keeping its hyperparameters, training rows and calibration method. PR-AUC is then measured on the June 2011 decision period. The test snapshot is never used.
- **Read the interval.** A paired bootstrap over decision-period customers gives a 95% interval for the loss.
  - *Necessary*: the interval stays above zero.
  - *Not shown*: the interval reaches zero or below, so the feature's contribution is not established.
- **Remove the candidates together.** Features that each look unnecessary can carry the same information; several pairs below are near-duplicates. So all "not shown" features are also removed together and tested once more.

### Findings

- **Twelve features earn their place.**
  - Recency matters most by far.
  - Next: purchase cadence (frequency, one-time buyer, average and spread of the gaps between orders), basket shape, category mix, time of day, and spend level and variability.
  - `avg_basket_size` is borderline: the lower end of its interval is effectively zero.
- **Thirteen features show no reliable contribution.**
  - *All three location features* (`country_code`, `is_domestic`, `n_countries`). Removing them also removes a stand-in for nationality or residence, a privacy and fairness gain at no measured cost.
  - *Exact duplicates.* `avg_basket_value` repeats `monetary_mean`, and `avg_unique_items_per_basket` repeats `avg_basket_size` (Spearman 1.00 in both cases). One of each pair is enough.
  - *The cancellation and return trio* (`has_ever_cancelled`, `cancellation_rate`, `return_rate`). They are almost the same signal (Spearman 0.97).
  - *Five others*: `monetary_total`, `max_basket_value`, `days_since_first_purchase`, `category_entropy` and `weekend_purchase_ratio`.
- **The 12-feature model scored higher, not lower.** Removing all 13 together gave a reduced model with a higher decision-period PR-AUC, and the whole interval points the same way.

**Recommendation.** Train the served model on the 12 necessary features. Keep all 25 engineered and documented above: the brief's feature-table requirement (section 3.2) is about breadth of engineering, while minimisation is about what the model actually uses.

### Not applied: this needs the project owner's decision

No feature has been removed. Applying the recommendation would:

- **Change the contract and its users.** That means the model contract (`src/contracts.py`), the API's request schema (exactly 25 values today), the interface's input form, the drift reference, the golden predictions and the tests that use them.
- **Change every reported metric.** The full training protocol would run again: model comparison, tuning, calibration and threshold.
- **Evaluate the test snapshot once more.** Decide from the development evidence above *before* seeing the new test result. Then report that result whatever it is; do not pick between the 25- and 12-feature models on the test snapshot.
